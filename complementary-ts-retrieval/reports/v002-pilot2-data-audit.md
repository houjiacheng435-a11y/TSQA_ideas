# 方向 3 · v002：先检查两道真实题，确定我们到底要研究什么

日期：2026-10-28。第一步数据审计；不是模型对比实验，也不是新方法结果。

## 1. 这一步要回答什么

我们想研究：系统能否找到**共同支持答案、并且时间和对象关系正确的一组时序证据**。

因此，第一步不是训练检索器，而是检查：准备使用的数据真的需要这种能力吗？现有系统答错，能否确定是组合证据出了问题？如果任务本身不能区分这些原因，后面即使提高了分数，也不一定能支撑我们想写的论文。

本次取回此前开发清单中已选定的两个 NLQTSBench 案例，核对原始数据、题目、标签时间和 Sonar-TS 的公开最终预测。它们此前已划为 `development_train`，且成功、失败状态已知，**只能用于理解任务和调试，不能充当独立测试集**。

**本轮结论：数据可以用于异常定位的开发检查；尚不能证明存在“证据组合失败”。暂不据此设计或训练新模型。**

## 2. 实际做了什么，哪些没有做

- 核对原始文件的 SHA-256，也就是用于检查文件是否逐字节一致的“指纹”；两个 CSV 均与历史清单一致。
- 使用 CPU 检查时间轴、数值、标签端点，重新计算公开预测的区间得分，画出原始曲线。
- 没有下载模型、调用模型 API、使用 GPU、训练、生成新题、修改原始数据或覆盖旧结果。公开预测是作者已发布的结果，不是本轮新运行的结果。

## 3. 两道题具体是什么

| 检查项 | 00395 | 00419 |
|---|---|---|
| 完整 ID 后缀 | `Causal_Anomaly_00395` | `Causal_Anomaly_00419` |
| 题目大意 | 已知上下游关系，寻找下游异常变平的时间段 | 已知上下游关系，寻找下游与上游反向变化的时间段 |
| 指定通道 | `155_up_2020`、`155_down_2020` | `680_up_2019`、`680_down_2019` |
| 数据范围 | 2020 全年，35,136 行 | 2019 全年，35,040 行 |
| 采样间隔 | 每 15 分钟一次 | 每 15 分钟一次 |
| 标注区间 | 2020-04-10 14:45 至 04-15 20:30 | 2019-05-19 15:00 至 05-23 01:45 |
| 作者公开预测 | 2020-04-10 17:45 至 04-15 17:45 | 2019-06-29 12:00 至 07-05 12:00 |
| 本次复算区间 IoU | 0.9542743539 | 0 |

IoU 是“两个时间区间重叠的时长 ÷ 两个区间并集的时长”。1 表示完全重合，0 表示不重合；0.954 不能解释成“95.4% 的题答对”。本次复算与公开分数一致。

两份文件均有且仅有时间戳、上游、下游三列；时间严格每 900 秒递增，没有重复时间或间隔缺口，两个信号没有空值或非有限数，标注的起止时刻均在原始时间轴中。公开预测文件中的参考标签与任务文件一致。

这些检查验证了文件完整性、记录对应和分数复算。**它们没有独立证明标注区间是唯一正确答案，也没有审计异常注入程序。**

## 4. 数据中实际看到了什么

### 00395：标注区间中的“变平”很清楚

标注区间内，上游数值范围为 0.107–0.176；下游只在约 0.14552–0.14644 之间轻微波动。下游的标准差约为 0.000146，明显小于紧邻前后、相同点数窗口的约 0.01184 和 0.01314。

标准差可以理解为“数值波动有多大”。这里原始数据支持“下游几乎不动，上游仍有变化”的描述，公开预测也基本覆盖标注。

**对研究的帮助：** 这是一个直观的开发检查案例。但仅看下游的异常平坦也可能找出该区间，尚未证明两个通道都是不可缺少的证据。下一步必须加入“只看下游”的简单数值基线，才能判断跨通道比较是否真的提供了额外价值。

### 00419：公开系统选错了月份，但还不知道错在哪一环

标注区间内，上下游的 Pearson 相关系数约为 **−0.225**；公开预测区间内则约为 **+0.914**。这与公开预测没有定位到标注的反向区间一致。

相关系数衡量两个信号在同一批时间点是否一起变化：接近 +1 表示较强同向，接近 −1 表示较强反向，接近 0 表示线性关系较弱。它本身不是因果证据，也不等于趋势方向或异常检测的完整定义。

这道题的标注区间并不是肉眼非常整齐的两条反向曲线：上游波动较小，标准差约 0.0281；下游夹杂较强波动，标准差约 0.0926。它更适合检查在噪声下的局部关系判断。**不能因为相关系数只有 −0.225 就判定标签有错，也不能凭这一个数字就确认标注正确。**

**对研究的帮助：** 它提醒我们先排除“局部形状或关系识别不准”和“搜索时根本没找到正确时间段”。本次取得的 `per_task.json` 只提供最终预测，没有足以还原检索过程的候选和执行轨迹，所以还不能把这次失败归因于证据组合。

这里所有“标注区间内”的统计都使用了已知标签，只用于解释数据。它们不是一个不看答案就能定位异常的算法，不能作为新方法成绩。

## 5. 为什么这两题还不足以支撑原来的论文设想

两道题都已在题目中指定上下游通道，CSV 中也只有这两个已对齐的通道。系统仍需从全年历史中定位异常，但不需要从许多设备和变量中决定“该选哪两个对象”。

因此必须分清：

| 可能的问题 | 本轮是否确认 |
|---|---|
| 文件读取或公开分数复算出了错 | 本轮未发现；上述基础检查通过 |
| 局部变化不容易识别 | 00419 提供了值得进一步检查的线索，还没有做盲测 |
| 候选检索没有覆盖正确时间段 | 没有过程轨迹，尚不知道 |
| 正确片段都在候选中，仍选了时间或对象关系错误的组合 | 没有证据确认；不能由最终答错推出 |
| 正确证据已经交给回答器，回答器仍答错 | 没有过程证据确认 |

`Causal Anomaly` 是数据集的任务名称；本轮做的是已知通道关系下的异常检查，没有从观测数据中证明真实因果关系。

## 6. 下一步顺序，以及每一步可能带来的论文价值

**下一步先做小规模 CPU 基线设计，不急着跑大模型。**

1. **比较单通道检测与双通道关系检测。** 在这些开发题上，预先记录窗口长度、评分和候选生成规则，然后比较只看下游的平坦程度，与同时看上下游的相关性、偏离程度。定位时不能使用标签区间，也不能预先知道异常时长。标签只在输出候选后用于评估。两题已经暴露，只能调试，不能声称泛化性能。
   - 可能发现：单通道规则已经足够，说明题目不适合证明证据互补；或双通道比较确实增加信息，值得扩大核验。即使简单规则成功，也能帮助我们及时收窄研究范围。
2. **从已有题目元数据筛查真正需要关系组合的任务，再确定是否值得下载更多。** 检查是否存在多个合理候选、同类事件出现在不同时间或对象、必须结合先后或延迟关系才能排除错误答案的题。优先使用现有数据，不先制造难题。扩展原始数据下载前说明规模并征得同意。
   - 可能发现：当前数据集不能检验我们的问题，应换任务；或能找到合适子集，才有条件研究组合选择。
3. **在合适子集上把错误分成四环：单段识别、候选覆盖、组合选择、最终回答。** 同时保留简单时间关联基线：当事件和关系条件都已明确时，直接按通道和时间规则匹配。如果这个基线足够好，就不能仅为了训练模型而增加复杂度。
   - 可能发现：候选齐全、单段判断正确时，现有强方法仍稳定选错组合，才直接支持当前候选研究问题。若主要是候选遗漏或局部感知错误，应调整方向。
4. **最后才决定 GPU / API 实验。** 需要先固定任务、样本数、比较方法和过程记录方式，再说明能排除什么假设、预计耗时与费用，获得同意后执行。本轮没有产生这类调用。

此前查新已经说明，通用“互补证据”“整组评分”和“根据已有证据继续检索”都有先例，详见 v001。上述检查的作用是找清楚一个具体、可验证的问题；现在还没有确认新的论文贡献。[SetR](https://aclanthology.org/2025.acl-long.861/)、[ParaSet / SetCE](https://arxiv.org/html/2607.05712v2)、[Sonar-TS](https://arxiv.org/html/2602.17001v3)。
