# 方向3 · v017：Conditional Complementary Evidence Retrieval

日期：2026-10-31（北京时间）。本轮先做固定程序与CPU必要性审计，再做小规模GPU检查。复用本地 Qwen3-8B 和 v016 环境，没有训练、付费API、权重下载或扩大原 Benchmark。

**结论：我们构造出了“当前材料无法确定答案，补对一份材料后才能确定”的动态取证任务。但普通覆盖规则＋数值匹配已达到 Oracle，不支持为这套任务训练新检索模型。Qwen自己的充分性判断和最终计算仍有错误，必须与检索成绩分开。Sonar-TS适配预检没有达到公平比较条件，本轮不提供其有效性能排名。**

## 1. 先确认 v016 的失败是不是代码造成的

选择4个代表性案例，不扩大原题库。直接将题目参数正确填入官方技能库中的固定Python程序，使用原数据库和官方评分器，不调用Qwen生成代码，也不拿参考答案替代算法。

| v016题号 | 原分数 | 固定程序分数 | 实际说明 |
|---|---:|---:|---|
| CA-00386 | 0 | 0.922 | 程序可以读取两条通道并定位异常；原运行的类型错误是重要干扰 |
| CT-00014 | 0.200 | 0.600 | 修正趋势类别后提高，但仍非满分 |
| CT-00025 | 0 | 0 | 模式正确填成“上升→上升”后，SAX筛出的20天仍漏掉全部5个标准日期 |
| CT-00034 | 0 | 0 | 回退后读取全年365天，5个标准日期全在，数值排序仍未命中 |

CA、CT的完整ID沿用v016，固定代码和原始输出保存在本轮记录中。“固定程序正确”在这里指**参数与程序实现按既有规则填写正确**，不意味着官方启发式一定等于数据生成时的标注规则；后两题正说明不能作这种保证。

因此，v016至少混合了代码生成、候选筛选和数值判定/标注定义三个问题。CT-00025有实际检索遗漏，但不是“多份材料必须联合选择”的证据；CT-00034则不能归因于没取全材料。这4题用于排除干扰，不作为新方法成绩。

## 2. 新任务是什么？结合一个例子说明

每个运行片段有两条目标通道P、Q。问题是：**两条通道是否都有短脉冲，而且Q的脉冲是否恰好比P晚2个采样点？** 初始只看到其中一条通道的完整42点记录。

例如，已经看到P在第8点开始脉冲：

| 与这份P属于同一运行片段的Q | 正确答案 |
|---|---|
| 第10点开始脉冲 | YES |
| 第29点开始脉冲 | NO |

在这两个反事实世界里，**初始P、问题、整个候选索引都逐字相同**。不实际取到Q的脉冲记录，无法判断是哪一个世界。固定Q、改变P时也构造相反答案。这沿用v015的2×2反事实方阵，而不是根据模型答错来猜测材料不足。

但不是每题都必须再取一份。如果当前目标通道的完整42点记录中没有脉冲，那么“两条都有脉冲”已经不成立，可以直接回答NO。缺P、缺Q和无需补充三种情况都包含在内。

### 候选池如何防止只认名称或位置？

每题有8个候选：P与Q各有同一运行片段、错误运行时段、近似上下文三份记录，另有两条无关通道。同一运行片段中已经看到的通道也是冗余候选。

每份记录除了目标信号，还带8个数的“上下文波形”，用来识别它属于哪个运行片段。候选索引只给其中前4个上下文数，不给脉冲时刻或脉冲原始值。正式取回后才能看到完整上下文和42点目标信号。

同一目标通道的三个候选名称、时间范围完全一致；各运行片段都用重新起算的0到41局部时钟。正确项、错误时段项、近似项没有文字标签，候选ID为不带语义的字符串。正确位置通过8种顺序旋转平衡，YES与NO的必要证据在每个位置出现次数相同。

因此，仅凭名称、时间范围或位置，无法区分这三个候选；需要看上下文的数值内容。不过，这个设计有一个重要边界：**上下文是严格匹配，索引已经很容易揭示对应关系。它适合验证取证与评分接口，却还不是困难的真实语义检索。**

## 3. CPU审计和数据访问限制

生成8个合成家族，每个家族有8个反事实/初始通道组合，加2个无需检索的无脉冲控制，共80个世界/初始状态；每个再做8种候选顺序旋转，共640个评估条目。**640不是640道独立自然题。**

| 审计项 | 结果 |
|---|---:|
| 初始证据不足 | 512/640 |
| 初始已足够，可直接停止 | 128/640 |
| 完全相同的公开初始视图，同时对应YES与NO | 256组 |
| 每个不足状态，补入正确候选后可确定答案 | 512/512 |
| 不足状态中，冗余、无关、错误时段或近似项能否替代正确候选 | 均不能 |
| 所有可确定状态的数值答案与构造标签一致 | 640/640 |

数值验证器只检查已经取得的记录：上下文是否匹配、是否为目标通道、脉冲是否存在、两个起点是否相差2。它不读取隐藏标签。初始索引也不包含目标脉冲信息。

每次 `fetch(candidate_id)` 只能取一个候选，预算最多2次；重复取同一ID或超预算会报错。生成程序运行在受限子进程，只有公开状态和通信接口，没有私有候选池或标签。文件读取、导入和内部属性访问被阻止。CPU边界检查确认正确程序可运行、越界请求会失败。这是受限诊断语言，不宣称是通用恶意Python安全沙箱。

Oracle可以访问正确候选ID来定义上界；其他规则的选择只用公开索引和已取得的证据。模型最终回答的提示词也不包含Oracle答案或数值验证器输出。

## 4. 普通规则已经解决了吗？是的

四种CPU对照使用同一候选池、预算和数值验证器：

- **独立相关性Top-K**：按目标通道是否相关、上下文距离逐项排序，不因某通道已经出现而降低其副本的分数。
- **覆盖率检索**：在相关性之外，优先覆盖尚未观察的目标通道。
- **当前状态规则**：先用数值验证器确认是否已能回答；不能时找出缺失通道，再按上下文匹配取回对应记录。
- **Oracle**：初始已够就停止，否则直接取唯一必要项。

覆盖率与状态规则在这套简单任务中事实上等价，不能把两种写法称为两项创新。所有方法都利用共同数值验证器停止；预算用尽且证据仍不足时输出UNKNOWN，不乱猜。

| CPU方法 | 预算1：必要证据取回率 | 预算1：数值答案正确率 | 预算2：数值答案正确率 | 预算2：每题平均取回次数 |
|---|---:|---:|---:|---:|
| 独立相关性Top-K | 50% | 60% | 100% | 1.2 |
| 覆盖率检索 | 100% | 100% | 100% | 0.8 |
| 当前状态规则 | 100% | 100% | 100% | 0.8 |
| Oracle | 100% | 100% | 100% | 0.8 |

“必要证据取回率”的分母仅为512个初始不足条目；答案正确率包含128个无需检索的控制。平均0.8次是因为20%的条目0次停止；**在真正需要补证据的条目中，状态规则每题1次，Top-K平均1.5次。**

独立排序第一条有一半机会是已有证据的副本；它没有利用“当前已经知道什么”。但加上普通覆盖规则就完全修正，或将预算从1增至2也能消除错误。反事实两端都答对且正确翻转的比例，预算1时Top-K为50%，其余100%；预算2全部100%。512个配对包含顺序旋转，不能当作512个独立统计样本。

这些CPU方法的 Sufficiency Accuracy 为100%、False Sufficiency Rate 为0，**因为我们直接提供了正确数值停止规则**。这不是检索器或语言模型学会充分性判断的证据。

## 5. Sonar-TS：尝试了，但不把不公平适配当作失败结果

原版Sonar-TS生成SQL/Python访问完整任务数据库，使用原任务的SAX特征和技能库。当前任务禁止访问候选池外的原始时序。若直接给完整数据库，就违反本轮访问约束；若改成受限取证接口，就改变了其运行环境与技能可用性。

因此单独实现协议预检：保留原仓库与Commit `99866c43cd7ceb91a929de745e9f49cea92962e5`，调用其规划、代码生成和错误修复函数；新提示词将运行接口改成 `index/fetch/verify`，代码最多重生成3次，已花费的检索预算不会因重试重置。原代码和v016实现未改动。

预检中，Qwen生成了复制后缺字段的候选表、占位信号、没有真正调用工具的“模拟验证”，也出现重复取证；另有一次错误源于受限接口未提供普通Python的 `next`。**后者属于适配限制，不能算作模型或检索方法缺陷。**

在4个完整预检和第5个部分运行后停止，保留24次已完成调用及1次主动中断请求。没有为了提高成绩更换题目或重跑到成功。这个版本不具有公平比较条件，因此：

- 不给出“Sonar-TS正确率低于规则”的方法排名；
- 不用占位程序或接口错误证明Sonar-TS不懂互补证据；
- 本轮有效方法比较只有前述4种CPU对照，**原定的第5项Sonar-TS公平比较未完成**；
- v016原任务上的Sonar-TS + Qwen3-8B仍保留，未被此次预检结果替代。

继续强行改造这个适配版本，对已经被简单规则完全解决的任务也不会产生有说服力的研究结论，所以没有扩大其测试。

## 6. 拿齐材料之后，Qwen自己会判断吗？

从一开始就固定第1、6两个家族，共20个条目：16个初始不足、4个初始可直接回答。没有按结果挑选或换题。先由状态规则取得实际证据，再让Qwen独立检查初始与取回后的原始数值，输出充分性及YES/NO/UNKNOWN；不把验证器结论交给它。

使用v016已有本地Qwen3-8B、vLLM 0.8.5.post1、BF16、非Thinking、temperature=0。20题共评估40个状态；4个无需取证的初始/最终输入完全相同，复用输出，因此实际36次调用。所有输出可解析，没有长度截断。

| 指标 | 实际结果 |
|---|---:|
| 规则策略取回必要证据 | 16/16 |
| 规则最终数值答案正确 | 20/20 |
| Qwen初始状态充分性判断正确 | 4/20 = 20% |
| Qwen False Sufficiency Rate | 16/16 = 100% |
| Qwen在完整最终材料下回答正确 | 12/20 = 60% |
| Qwen反事实两端均答对且翻转 | 0/16对 |

Qwen在这40个状态中都声称“充分”。因而混合状态下普通充分性准确率为60%，宏平均为50%；“最终材料下充分性100%”只是最终20个输入本来全都充分，不能证明模型会辨别不足。

这里的Qwen False Sufficiency Rate衡量**独立充分性声明**，不是一个已验证的闭环检索agent的实际提前停止率。如果直接拿这些声明作为停止信号，16个不足初始状态都会错误停止；本轮真正执行的CPU策略则由固定验证器控制，没有发生这种提前回答。Sonar-TS的闭环比较未完成，不能用这两个层面的数字代替它。

最终20题中，16题确实需要联合两条有脉冲的通道；Qwen将这16题全部答为YES，只答对其中8题。另4个无脉冲控制回答NO正确，所以合计12/20。这个60%混合分数不能解释成它已经稳定理解滞后关系。

本轮没有进一步分解数字阅读、脉冲定位与精确时间差计算的贡献，不能说这些错误全是充分性机制、时序编码或某一种内部原因造成。重要的是：**检索规则已经20/20把答案变得可确定，回答模型仍可能答错。** 两个层面的分数不可相互替代。

36次正式回答控制合计输入35168、输出756 tokens，本地LLM请求总耗时约18.46秒；适配预检另有24次完成调用，单独保存，不混进这36次。GPU服务在全部检查后停止，显存释放到约1MiB。

## 7. 三个研究问题的判断

**1）现有方法是否真的存在互补证据检索缺陷？**

本轮证明了一个具体、有限的问题：不考虑已有证据的逐项排序，会浪费紧张的预算选冗余材料。没有证明主流集合检索、动态检索方法普遍失败，更没有公平证明Sonar-TS失败。Top-K增加一次预算也能解决当前问题。

**2）简单规则或传统数值方法能否解决？**

能。缺哪条通道就补哪条，再做普通内容匹配和固定数值验证，已经达到Oracle。原因是上下文严格匹配、目标关系固定、必要材料唯一；这本质上接近一个内容匹配后的配对问题，而非复杂的条件价值推断。当前证据足够支持“不应为这套任务训练新检索器”。

**3）如果还不能解决，最值得改什么模型机制？**

本轮“不能解决”的前提没有成立，因此不建议马上训练。Qwen自身的过度充分性判断值得继续诊断，但给它配正确数值验证与停止门槛，就能在本任务中防止错误提前回答；尚未证明这需要新模型机制。

若继续方向3，下一步更有价值的CPU门槛是：上下文存在噪声或缺段，多个候选看起来都可能对应同一事件；不同初始内容使真正有价值的下一份材料发生变化；有些问题需联合3份以上，而不是补齐固定的另一通道。仍须用可枚举的反事实世界证明何时可确定，并先与数值匹配、集合覆盖和简单决策树比较，不能仅靠增加干扰项制造困难。

此时可研究的“条件证据价值”是：**新材料能排除哪些仍然可能的答案，收益是否值得一次检索成本？** 只有简单方法稳定达不到这个目标，且问题翻译、工具执行与最终计算已受控，才有理由训练选择/停止策略。目前还没有跨过这一门槛。
