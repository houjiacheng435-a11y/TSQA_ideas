实验日期：2026-10-31（北京时间；服务器 UTC 日志为 2026-10-30）。先完成一道完整 Smoke Test，通过后完成固定的10题；Smoke Test 计入10题，未重复推理。无外部付费 API、训练、新权重下载或全量 Benchmark。

**本地系统已经跑起来，可以作为后续对照。10题中8题完成代码执行，2题执行失败；片段匹配和综合分析有成功案例，异常和趋势排序暴露了代码与问题翻译错误。当前结果没有证明 Sonar-TS 存在“互补证据选择”缺陷，也不足以支持直接开发新的检索模型。**

开始时系统盘剩约25GB，数据盘剩约4.2GB；结束后分别剩约22GB、4.1GB。新 Python 依赖装在系统盘的独立环境；10题独立数据库约29MB。权重分片、索引和非 Thinking 模板检查通过。依赖安装时固定了兼容版本，未升级原有实验环境。

本次保留官方任务规划、技能选择、提示词、代码抽取、Python 执行、最多3次代码重生成、60秒执行超时、输出格式检查和最终格式化。接口改为本地 Qwen，HTTP 等待上限改为600秒，并记录请求、输出和 token 数。未发生 HTTP 错误；26次调用均正常结束，没有长度截断或可见 Thinking 块。

服务实际分配的KV缓存容量为35552 tokens；单次请求仍限制在16384 tokens，并发限制为1。默认前缀缓存只复用相同提示词前缀的计算，不复用前题答案；每次调用都单独提交完整messages。

另加只读数据库与观察日志：保存每条 SQL、返回的候选/原始片段、程序中间变量、stdout/stderr。CPU 自检确认加日志前后查询输出一致。日志开销计入执行和总耗时；测试前后原始CSV与新数据库的哈希均未变化。

## 2. 先把官方流程说清楚

实际流程是：**问题 → Qwen 制定计划并选择技能 → Qwen 生成整段程序 → 程序做 SQL 搜索和 Python 数值计算 → 检查执行与输出格式 → 确定性格式化答案。**

这里的“验证”有两层，必须分开：

- 生成程序内部应当从原始数据做数值验证；这段验证规则本身也可能生成错误。
- 框架检查程序是否报错、结果是否为指定类型，例如“两项时间组成的列表”。它不自动证明数值结论正确，也没有一个独立的“这些证据是否够了”判断器。

只有异常、超时或格式错误会触发 Qwen 修改代码。一个语义错误、但格式合格的时间区间会直接结束。最终回答由官方格式化函数生成，没有再调用一次 LLM 来重写答案。[官方流程实现](https://github.com/Atlamtiz/Sonar-TS/blob/99866c43cd7ceb91a929de745e9f49cea92962e5/sonar_ts/pipeline.py)

官方技能库还包含具体数值算法，例如标准化片段匹配、上下游方差/回归残差、趋势排序和分段分析。因此本轮测试包含“Qwen 能否正确采用已有算法”，不能解释成它从零发现了检索方法。[官方技能库](https://github.com/Atlamtiz/Sonar-TS/tree/99866c43cd7ceb91a929de745e9f49cea92962e5/sonar_ts/skills/library)

## 4. 结合例子，看清成功与失败在哪一步

### 成功：确实执行了数值匹配，而不只是连通 API

SM-00332 要求用 `2023-09-07 15:00:00` 至 `2023-09-08 03:15:00` 的参考形状，在指定后续区间中寻找相似片段。

模型选择 `subsequence-matching` 技能，生成程序，分别读取50个参考点与598个搜索点，做标准化滑窗距离比较，返回：

```text
[2023-09-15 03:45:00, 2023-09-15 16:00:00]
```

该区间与标准答案完全相同。完整流程17.10秒，2次LLM调用，无代码重试。这证明系统能够完成规划、查询、计算、执行检查、答案生成与官方评分的全链路。

IS-00001 则读取11月全部2880个点，生成“先 gradual rise，再 rapid rise”的两阶段报告，并准确定位异常时间 `2021-11-21 05:45:00`。阶段交界预测为11月21日14:00，标准为11月22日10:15，提前20小时15分，所以时间边界分不是满分。整体0.9806也不意味着每个细节完全正确。

### 失败一：已经拿到两条通道，程序却没运行完

CA-00386、00387 的查询记录中均包含两条上下游通道，以及标准异常所在时段的全部原始点。它们最终失败于 Python 类型错误，而不是因为没给到某个通道。CA-00386 连续四次都保留了 `str.strftime` 错误；CA-00387 第一次为 `NoneType` 索引错误，后面为 `int.strftime` 错误。

这些题只能说明本地 Qwen 的代码生成/修复不可靠。不能把零分当成“模型不会结合上下游证据”的证据。

### 失败二：没有找到候选，却把“整年”当成已验证答案

CA-00388 的标准异常区间是 `2022-04-06 07:45:00` 至 `2022-04-12 13:15:00`。生成程序先在年度特征表筛选：

```sql
std_val < (SELECT AVG(std_val) FROM yearly_feature WHERE channel_id = ?)
```

这份数据每条通道只有一条年度记录，因此该条件相当于要求“某个数严格小于它自己”，没有候选。SQL轨迹确认程序没有读取任何原始时序点。随后生成代码直接回退为：

```python
_result = ["2022-01-01 00:00:00", "2023-01-01 00:00:00"]
```

这个列表格式正确，框架就停止了，得分0.0171。这确实暴露出“不恰当停止”：没有证据也给出答案；但直接原因还包括错误的筛选代码。不能据此证明一个正确工作的检索器仍缺少互补选择能力。

### 失败三：有的漏在搜索，有的错在搜索之后

CT-00025 题目模式原文为 `'rapid rise, then slow rise'`，生成代码却设置 `kinds = ["fall", "rise"]`。因此筛出的45天不包含任何一个标准答案日期。这是可以直接定位的问题翻译错误，尚未涉及“多个相关候选怎样互补”。

CT-00014 则不同：SQL读取了241天，5个标准日期全部在里面。但代码把 `target_kind` 写成 `"slow rise"`，而数值函数只识别 `"rise"`、`"fall"`，其余走平稳分支，导致验证规则与问题不一致。

CT-00034 的初筛只有2天，不够输出5天，程序按官方技能中的回退规则读取全部365天。最终5个标准日期一个都没答中。其代码基本沿用了官方趋势排序配方，说明还需核对数值启发式与标注定义；这里不能归因于材料遗漏，也不能未经审计就断言官方规则或标签哪一方错误。

IS-00002 也读取了完整月份，但把中间的 gradual rise 写成 fluctuating stable，并移动了阶段交界。异常时间仍正确；这是分段/数值判断误差，没有观察到检索访问遗漏。

## 6. 与方向3有什么关系？下一步值不值得做？

**已经得到的可靠对照：** 这个系统可以把数值工作交给Python，避免要求LLM直接阅读长串数字。两道片段匹配满分、两道综合分析平均0.8551，是它在本小样本上有效的具体证据。后续新方法必须与这种“工具＋现成算法”比较，不能只和直接读数字的模型比较。

**关于完整证据：** 异常题有两题实际读取了两个通道；综合题读取整个月；趋势题既有候选遗漏，也有回退到全年。必须逐题看SQL和数值程序，不能将整个框架统一叫成“只看了一份证据”。读取全部原始点也不自动证明之后的关系判定正确。

**关于继续搜索：** 官方提示和趋势技能包含“候选为空/不足K个时扩大到原始数据”的规则，CT-00034确实这样执行了。这是已有的补搜机制。但它由生成程序中的分支实现，不是每拿到新证据后，都由一个独立模块判断还缺哪种互补信息。CA-00388则生成了错误回退；框架只看到格式合格，不会主动否决。

**关于真正的互补缺陷：** 本轮没有建立。v015证明了某些受控问题必须联合A+B才能唯一回答；v016证明了一个现有工具框架能够运行，但其失败混合了问题翻译、执行、数值启发式和停止逻辑。它们尚不能串成“现有方法不能检索互补证据，所以需要新模型”的论证。

这10道真实题本身也不能直接当成“不可替代互补证据”的证书。综合分析的阶段与异常可以分别报告；跨变量题给了上下游两个通道，也不意味着单通道必然无法答。v008等历史审计已检查过这类捷径。本轮没有对这10题新增反事实必要性证明，因此保留为系统基线测试，不把“任务看起来复杂”当作互补性的证明。

本轮也不计算 False Sufficiency Rate：这些官方题没有系统标注“当前显示不足”的输入条件，Sonar-TS也没有输出明确的充分性标签。凭错误回退案例给它计算该指标会混淆定义。“数值验证正确但LLM最终改错”的情况亦未在此流程中观察到，因为最终文本不是LLM再次生成的；官方报告格式化统一使用 spike 措辞，因此异常峰/跌语义也不能只凭该措辞判定。

**建议保留这套本地基线，暂不直接扩大到100题或全量。** 下一轮先做一个小而明确的CPU对照：绕过Qwen的规划/代码填写，用固定程序直接调用官方数值配方，分清“配方本身近似”与“Qwen把配方用错”。然后再把经过必要性审计的A、B及干扰材料接入这个工具环境，测试是否识别缺哪条通道或哪个时段，并与普通“缺字段就补字段”规则比较。该测试才更接近方向3的条件证据价值问题。

原版DeepSeek仍有后续对照价值：可判断这些代码/规划失败多大程度来自8B替换模型；但它不能自动证明互补检索已经解决或尚未解决。本轮没有使用或开通该API，先保留为下一阶段选项。
