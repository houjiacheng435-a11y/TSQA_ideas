# v019 CPU reproduction

This experiment makes no LLM calls, imports no model framework, and starts no GPU jobs. It audits published predictions and executes fixed, trusted source templates. These CPU traces are not recovered official model traces.

## Sources and environment

- Sonar-TS: https://github.com/Atlamtiz/Sonar-TS at `99866c43cd7ceb91a929de745e9f49cea92962e5`.
- Result-version template: `f2d61852498f1e406effc9d2696c512d2b3a2180`, obtained with `git show`; not generated by a model.
- Dataset: https://huggingface.co/datasets/mrtan/NLQTSBench/tree/81571171c5c614d01698497626bff8eb6ad8dcf4.
- Python 3.12.3; NumPy 1.26.4; Pandas 2.2.3; SciPy 1.14.1. Matplotlib is needed only for `illustrate.py` (actual version recorded in environment.json).
- Reused interpreter on the original server: `/root/v016-sonarts-env/bin/python`. No new package installation was necessary.

Keep a full Git checkout of the official repository at the pinned commit so `git show` can read the earlier template. Set `SONARTS_ROOT` to that checkout. The runner checks the commit and verifies audited source bytes against committed blobs.

## Execute

From the TSQA_ideas repository root, with the above CPU packages available:

```bash
export SONARTS_ROOT=/path/to/pinned/Sonar-TS
export V019_OUTPUT=/tmp/v019-new-reproduction-001
export OPENBLAS_NUM_THREADS=1
export OMP_NUM_THREADS=1
python complementary-ts-retrieval/experiments/v019-cpu-failure-atlas/run.py audit
python complementary-ts-retrieval/experiments/v019-cpu-failure-atlas/run.py acquire
python complementary-ts-retrieval/experiments/v019-cpu-failure-atlas/run.py run
python complementary-ts-retrieval/experiments/v019-cpu-failure-atlas/run.py score
python complementary-ts-retrieval/experiments/v019-cpu-failure-atlas/audit_semantics.py
python complementary-ts-retrieval/experiments/v019-cpu-failure-atlas/version_check.py
python complementary-ts-retrieval/experiments/v019-cpu-failure-atlas/legacy_interventions.py
python complementary-ts-retrieval/experiments/v019-cpu-failure-atlas/extend.py
python complementary-ts-retrieval/experiments/v019-cpu-failure-atlas/illustrate.py
```

Use a fresh output directory for each run: timing values differ, and JSON outputs refuse replacement with different content. Do not point a new run at the committed result directory. All raw CSVs live under the project's untracked `data/`; selected existing CSVs are reused only after verifying their pinned upstream hash. Missing selected CSVs are downloaded with direct IPv4 curl from hf-mirror, never model files. `raw-file-catalog.json` contains the 16 needed upstream file entries, extracted from the previously acquired full file catalog. Each file must match its size and Git Blob/LFS hash. No full dataset download is required.

## Experimental boundaries

- `protocol.json` froze the original 12 CT cases and primary interventions before raw inspection. This score-stratified case sample does not estimate population performance.
- `run.py run` reads only public-inputs and raw-manifest, never answer/meta/published-prediction files. Evaluation labels are read separately by `score`.
- `audit_semantics.py` is post-hoc evaluation only and is not imported by the prediction runner. Metadata injection dates/boundaries are not retrieval inputs.
- Version diagnostic and legacy-intervention protocols were added after discovering that output JSON predates the current CT template. All original 12 cases were retained. There was no parameter search.
- `extension_protocol.json` freezes four illustrative shape/causal cases before acquiring their data. It adds no claim of task-wide performance.
- Raw access differs by version: current CT template usually queries candidate days only; old CT template queries the full year. Removing old SAX priority changes only final priority, not raw access or numerical floor.
- The independent piecewise-linear diagnostic is deliberately limited: minimum four points per segment, sign constraints only, no adjective thresholds, no tuned floor. It is neither an oracle nor a complete task solution.

## Outputs

- `official-audit.json`: 1,153 rescoring checks, file/version hashes, per-task metric distributions.
- `official-case-catalog.json`: traceable IDs for all 444 CT/SI/CA cases; evaluation-only material.
- `cases/`, `sql-traces/`, `day-metrics/`, `daily-features/`, `executed-code/`: current-template CPU reconstruction and interventions.
- `legacy-template-results.json`, `legacy-template-scores.json`, `executed-code-legacy/`: result-version template reconstruction, matching all 12 published CT date sets.
- `legacy-interventions*.json/csv`: single-factor version-matched interventions.
- `semantic-audit.json`: label/source definition checks; not a prediction input.
- `extension/`: four fixed additional cases, raw access, SQL, code, predictions, IoU.
- `illustrative-case.json` and PNG: actual measured interval for CT00007; post-hoc illustration.
- `raw-manifest.json`, `extension/raw-manifest.json`: paths, exact dataset revision, file integrity identifiers.
- `reproducibility-check.json`: all 12 primary cases re-executed in a fresh directory; every non-timing case field and full day-metric file identical.

The original primary numerical run took 23.48 seconds total for 12 cases (excluding acquisition and other audit stages). This is CPU program time, not a model inference latency estimate. No GPU rental or paid API charges were incurred by this experiment. Existing server CPU use is not a claim of zero server rental cost.
